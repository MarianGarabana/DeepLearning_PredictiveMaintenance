# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Student deep-learning project (IE University, presentation June 30 2026): predicts **Remaining Useful Life (RUL)** of turbofan engines from multivariate sensor time series. The deliverable is a deployable MVP — a trained Keras model served by a FastAPI backend, with a **React** dashboard (Week 2) deployed to Vercel that calls the backend over HTTP. Dataset is NASA CMAPSS FD001 (committed in `data/raw/`).

## Commands

```bash
# Environment (notebooks + backend share one conda env)
conda create -n dl_project python=3.11 -y
conda activate dl_project
pip install tensorflow==2.15.0          # install first, separately
pip install -r requirements.txt         # root = full local-dev set (notebooks + API)
python -m ipykernel install --user --name dl_project   # then select kernel in IDE

# Run backend locally (serves on :8000)

# Build/run the deployment image (Hugging Face Spaces, port 7860)
docker build -t pdm-api .               # uses the ROOT Dockerfile, build context = repo root
docker run -p 7860:7860 pdm-api
```

There is **no automated test suite**. Verify changes by hitting the running API (`/health`, then `POST /predict`, or `POST /simulate/start` → `GET /simulate/next/{id}` to exercise inference with demo data). Notebooks are run interactively in order 01 → 02 → 03 → 04.

## The critical invariant: preprocessing parity

`backend/predict.py::_preprocess` **must mirror `notebooks/02_preprocessing.ipynb` exactly.** Inference and training share the same MinMaxScaler, the same dropped sensors, the same column order, and the same 30-cycle sliding window. If you change preprocessing in the notebook, you must retrain (regenerating `scaler.pkl` + `lstm_model.keras`) and update `predict.py` to match, or predictions silently corrupt.

Non-obvious details of this pipeline:
- **`scaler.pkl` is not just a scaler.** It's a dict (loaded as `_META`) holding `scaler`, `feature_cols`, `drop_sensors`, `sequence_length`, and `rul_cap`. Read config from it; don't hardcode.
- **Feature count: 24 → 17.** Raw rows are 3 operational settings + 21 sensors. 7 constant-variance sensors are dropped during preprocessing, leaving 17 features.
- **Frontend sends only 21 raw sensor values per cycle** (no op settings). `predict.py` prepends `DEFAULT_OP_SETTINGS = [0.0, 0.0, 100.0]` because FD001's `op_set_3` is constant 100 — zero-padding it would push scaled inputs outside the training range.
- **RUL is capped at 125 cycles** in training; the model never predicts above that.

## Model loading gotcha

The model uses a custom `DotProductAttention` Keras layer. It must be passed via `custom_objects={'DotProductAttention': DotProductAttention}` to `keras.models.load_model` — the class is redefined inline in `predict.py::_load`. `predict.py` loads the model **at import time** (warm start) inside a try/except, so the server boots even if model files are missing.

The deployed model (`backend/model/lstm_model.keras`) is **LSTM+Attention**, and `metrics.json` reflects it — even though GRU scored marginally better on this small dataset. Don't "fix" that mismatch.

## Demo data is shared by backend and frontend

`frontend/public/demo-data/engine_{healthy,degrading,critical}.json` are pre-recorded sensor sequences generated by `notebooks/04_evaluation.ipynb`. They serve two consumers:
1. The frontend reads them directly for the live "Simulate" demo (never depends on live inference).
2. The backend `/simulate/*` endpoints also read them (note `main.py` builds the path as `../frontend/public/demo-data`), and the **root Dockerfile copies this folder into the image** so deployment works.

Each row is `{cycle, sensors:[21 floats], rul}`. When a row's `rul` is present it's used directly; otherwise the backend runs live inference (padding the single row to a 30-cycle window).

## RUL → status thresholds (used everywhere)

`utils.py::rul_to_status`: `< 30` → `CRITICAL`, `< 80` → `WARNING`, else `OK`. Status is always *derived* from RUL, never stored independently — keep it that way across backend and frontend.

## Backend shape

`main.py` (6 endpoints) → `predict.py` (inference) / `utils.py` (NASA score, status, CI) / `schemas.py` (Pydantic contracts). Things that look real but are placeholders for the MVP demo: `/fleet` returns 6 hardcoded engines, `/engine/{id}` returns fixed data, and `_simulate_sessions` is an in-memory dict (won't survive a restart or scale past one worker — fine for the demo, would need Redis for prod). The confidence interval is a flat ±15%, not a real uncertainty estimate.

## Pinned dependencies — do not bump casually

`tensorflow==2.15.0`, `keras==2.15.0`, `scikit-learn==1.8.0`, `numpy>=1.24,<2.0`. The scaler was pickled with sklearn 1.8.0 and the model with TF/Keras 2.15 — version drift breaks unpickling/model load. On Apple Silicon, do **not** add `tensorflow-metal` (it crashes on this TF version); training runs on CPU (~20 min on M4).

## Two Dockerfiles

- **Root `Dockerfile`** — the real one. Build context is the repo root; copies `backend/` + `frontend/public/demo-data/`. Use this for Hugging Face Spaces (see `docs/huggingface_deployment.md`).
- **`backend/Dockerfile`** — older single-folder variant (`COPY . .` from inside `backend/`). It does **not** include demo-data, so `/simulate/*` will 404. Prefer the root Dockerfile.

Model artifacts (`.keras`, `.pkl`, `.npy`) are tracked via Git LFS (`.gitattributes`). `data/raw/` is committed; `data/processed/*.npy` is gitignored (regenerate via notebook 02).
